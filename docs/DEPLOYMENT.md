# Cloud deployment (Render)

Production runs on **Render**, defined in [`render.yaml`](../render.yaml):

| Resource | Render type | Notes |
|---|---|---|
| `adminflow-db` | Managed PostgreSQL 17 | Private: no public IP allow-list. Daily backups on paid plans. |
| `adminflow-api` | Web service from image `ghcr.io/<owner>/<repo>/backend` | Health check `/health`, auto-restart, secrets generated by Render |
| `adminflow-web` | Web service from image `ghcr.io/<owner>/<repo>/frontend` | Health check `/healthz`, proxies `/api` to the API |

Why Render: it has a free tier, managed TLS, a managed Postgres, zero-downtime deploys, and a Blueprint file that keeps infrastructure in Git. The images are standard OCI images, so the same CI output also runs on Azure Container Apps, AWS ECS or Cloud Run (see the end of this page).

## One-time setup (about 20 minutes)

### 1. Push the repo to GitHub and let CI publish images

```bash
git init && git add . && git commit -m "AdminFlow Month 5: containerised fullstack with CI/CD"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
```

The first run builds and pushes both images to GHCR. The deploy job then fails with "Set RENDER_DEPLOY_HOOK_…". That is expected, because Render does not exist yet.

Then make the two packages pullable by Render. Either:
- GitHub → your profile → Packages → `backend` and `frontend` → Package settings → **Change visibility → Public** (simplest), or
- keep them private and add a registry credential in Render (Account settings → Registry credentials, GitHub PAT with `read:packages`), then uncomment `creds` in `render.yaml`.

### 2. Create the infrastructure from the Blueprint

1. In `render.yaml`, replace `OWNER/REPO` with your **lower-case** GitHub path, commit and push.
2. Render dashboard → **New → Blueprint** → connect the repo → **Apply**.
3. Render creates the database, generates `JWT_SECRET` and `METRICS_TOKEN`, and injects `DATABASE_URL`.
4. On first boot the API waits for the database, applies migrations and seeds the demo data. Check its logs for `Applied migration` and `API listening`.
5. If Render gave the API a different hostname (for example `adminflow-api-x1y2.onrender.com`), update `API_UPSTREAM` on **adminflow-web** to match.

### 3. HTTPS and custom domain

- Every `*.onrender.com` URL is HTTPS by default with a managed certificate. HTTP redirects to HTTPS.
- Custom domain: adminflow-web → Settings → **Custom Domains** → add `app.example.com`, create the `CNAME` it shows at your DNS provider, and Render issues a Let's Encrypt certificate automatically. Renewal is automatic.
- HSTS: once the domain is final, add `Strict-Transport-Security "max-age=31536000"` to `frontend/nginx.conf.template`.

### 4. Connect CI to Render

| Where | Name | Value |
|---|---|---|
| GitHub → Settings → Environments → `production` → Secrets | `RENDER_DEPLOY_HOOK_BACKEND` | adminflow-api → Settings → Deploy Hook URL |
| ″ | `RENDER_DEPLOY_HOOK_FRONTEND` | adminflow-web → Settings → Deploy Hook URL |
| ″ → Variables | `API_URL` | `https://adminflow-api.onrender.com` |
| ″ → Variables | `PRODUCTION_URL` | `https://adminflow-web.onrender.com` (or your domain) |

Re-run the failed workflow (or push to `main`). From now on, every merge to `main` deploys automatically.

### 5. Verify

```bash
curl -s https://adminflow-api.onrender.com/health | jq    # status: healthy, version: sha-…
curl -sI https://adminflow-web.onrender.com | head -1     # HTTP/2 200
```

Then open the production URL and sign in with `admin@adminflow.io` / `Admin@123`.

## Environment variables

| Variable | Service | Default | Purpose |
|---|---|---|---|
| `DATABASE_URL` | API | — | Postgres connection string (from the Render database) |
| `DATABASE_SSL` | API | `false` | Set to `true` when connecting over a public, TLS-only endpoint |
| `JWT_SECRET` | API | — | **Required in production**. The API refuses to start without it. |
| `JWT_EXPIRES_IN` | API | `8h` | Session length |
| `METRICS_TOKEN` | API | empty | If set, `/metrics` requires `Authorization: Bearer <token>` |
| `LOG_LEVEL` | API | `info` | `error`, `warn`, `info` or `debug` |
| `DB_POOL_MAX` | API | `10` | Postgres pool size per instance |
| `TRUST_PROXY` | API | `1` | Proxy hops in front of the API, so rate limiting sees the real client IP |
| `SEED_ON_START` | API | `true` | Seed demo data into an empty database |
| `API_UPSTREAM` | Web | `http://backend:3000` | Where nginx forwards `/api` |
| `PORT` | both | 3000 / 8080 | Listening port |

## Blue-green deployment and rollback

Render's zero-downtime deploy works the same way as a blue-green switch:

1. **Green** (the new image) starts next to **blue** (the running version).
2. Render polls green's health check (`/health`, which includes a database round-trip).
3. Only after it passes does traffic move to green. Blue then receives SIGTERM and drains in-flight requests (the API handles this with a graceful shutdown).
4. If green never becomes healthy, the deploy fails and **blue keeps serving**. Users see no outage.

Two versions can briefly run against the same database, so migrations must stay backward-compatible (expand, then contract). The migration runner holds a Postgres advisory lock, so only one instance applies them.

**Rollback** (no rebuild): GitHub → Actions → CI/CD → **Run workflow** → `rollback_tag = sha-<previous>`. This redeploys that exact image through the same health-gated switch. You can also click **Rollback** on a previous deploy in the Render dashboard.

Running blue-green by hand on any Docker host works the same way. Start the new tag under a second Compose project (`IMAGE_TAG=sha-new docker compose -p adminflow-green up -d --wait`), switch the reverse proxy upstream, then `docker compose -p adminflow-blue down`.

## Free-tier caveats

- Free web services sleep after 15 minutes idle. The first request then takes about a minute (cold start). Upgrade to Starter for always-on.
- Free Postgres instances expire after 30 days and have no backups. Use a paid plan for real data.

## Alternative: Azure Container Apps

The same images run unchanged on Azure Container Apps:

```bash
az group create -n adminflow-rg -l southeastasia
az postgres flexible-server create -g adminflow-rg -n adminflow-pg --tier Burstable --sku-name Standard_B1ms --version 17 --public-access None
az containerapp env create -g adminflow-rg -n adminflow-env -l southeastasia
az containerapp create -g adminflow-rg -n adminflow-api --environment adminflow-env \
  --image ghcr.io/<owner>/<repo>/backend:sha-<commit> --target-port 3000 --ingress internal \
  --secrets jwt=<secret> db=<connection-string> \
  --env-vars JWT_SECRET=secretref:jwt DATABASE_URL=secretref:db DATABASE_SSL=true NODE_ENV=production
az containerapp create -g adminflow-rg -n adminflow-web --environment adminflow-env \
  --image ghcr.io/<owner>/<repo>/frontend:sha-<commit> --target-port 8080 --ingress external \
  --env-vars API_UPSTREAM=http://adminflow-api
```

Container Apps gives HTTPS on its `*.azurecontainerapps.io` domain and supports **revision-based blue-green** (`--revisions-mode multiple`, then shift traffic with `az containerapp ingress traffic set`). In CI, replace the Render hook step with `azure/login` + `az containerapp update --image …`.
